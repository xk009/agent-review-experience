# 一周试用：审阅是否真的更快且可靠

这是待执行的试用方案，不是已取得的效果报告。

## 比较方式

选择相近规模的代码、文档或分析任务，记录原工作流与新工作流。
第一阶段只增加 Review First；第二阶段再加交付包；仅对需要的任务增加独立预审。
不要同一天把字体、主题、Agent 和报告形式全部改变后，就把改善归因到某一个因素。
小样本用于发现具体摩擦，不用于宣称统计显著性。

## 主要观测

| 记录项 | 口径 |
| --- | --- |
| 人工审阅时间 | 开始阅读到作出接受 / 退回 / 补验决定的活跃时间；暂停等待单列 |
| 找证据次数 | 从摘要转去搜文件、日志、版本或任务记录的次数 |
| 澄清次数 | 为问清变化、验证范围或风险而新增的追问 |
| 等待与生成成本 | Agent 生成、测试、预审等待分别记录；实际用量无法获得就写未知 |
| 遗漏与返工 | 后续暴露的问题及额外修改轮次，不能只看第一次读得多快 |

一次只记一分钟以内能完成的数据；不要让测量本身变成重负担。

## 记录模板

```text
任务 / 日期：
类型 / 规模 / 风险：
工作流：原始 / Rule / Rule+Package / 加独立预审
人工活跃审阅分钟：
等待分钟（Agent / 验证）：
找证据 / 澄清次数：
首次决定：接受 / 退回 / 补验
后续遗漏 / 返工：
最有帮助的一项 / 最多余的一项：
```

## 客户端验收清单

- 新会话能识别已安装的 `review-first.md`；简单问答不套四段模板。
- `/review-package` 能手动调用；未调用时不自动启动长流程。
- 一个包含暂存、未暂存和相关新增文件的样例任务，没有漏报变化。
- 修改同一 HEAD 下的工作区后，旧证据被标明过期，而不是继续显示已验证。
- 未执行测试时如实显示未验证；编译结果不冒充业务验收。
- 请求独立预审时，实际启动只读子代理；失败时如实说明。
- 第二轮突出增量和失效证据，仍保留原始变化入口。
- 若生成 HTML，关键失败、风险和验证缺口首屏可见，窄屏可读。

这些需要在实际 Claude Code、终端和业务任务中执行。Python 安装器测试通过不等于以上验收已通过。

## 一周后的保留标准

优先保留同时降低找证据和澄清负担、且不增加遗漏的部分。
若小任务的报告比代码还长，缩减为终端摘要＋真实 diff；不要为了统一形式增加成本。
若预审新增等待很多但有效发现少，降低触发频率，优先覆盖高风险或不熟悉的代码。
