# 可复制的审阅提示词

未安装 Skill 时可单独使用；已安装时优先使用 `/review-package`，不要把整套长流程塞进全局 Rules。
这些是任务指令，不是强制安全机制。替换尖括号，不直接执行占位符。

## 1. 准备审阅交付包

```text
请为当前任务准备审阅交付包，不修改业务代码，不提交或推送。
任务和验收目标：<填写>。
比较基线和纳入范围：<填写；不能确定时先指出缺口>。
先给结果、关键变化、优先人工审阅点、验证与缺口。
把每个关键结论连接到真实 diff、源文件或验证证据。
代码任务区分已提交、暂存、未暂存和相关新增文件，绑定源版本和内容快照。
明确实际执行的验证、未验证项和历史证据；不要把实现完成说成验收通过。
小任务保持轻量；复杂材料写成 Markdown，终端只给摘要和入口。
```

## 2. 独立预审，而非自动修复

```text
请调用已安装的 review-auditor，对本次任务做只读独立预审。
输入以需求、验收标准、真实 diff、源文件、快照和已有验证证据为准，
不要把实现者的自评当作正确性证明。
优先检查正确性、兼容性、状态边界及验证缺口。
每个发现给具体位置、触发条件、错误后果、依据和最小验证方法。
不修改代码，不自动修复、提交或批准合入。
主会话负责准备 diff；如果无法启动独立子代理，如实说明，不能把同会话自查冒充独立预审。
```

## 3. 第二轮只审新增变化

```text
请对照上一轮审阅包 <路径或版本>，准备本轮增量审阅。
先列：新增变化、修改项、已解决问题、仍待处理事项。
逐项说明上一轮哪些验证仍适用，哪些因本轮变化失效。
不要重述所有已确认内容，但新出现的关键风险必须保持可见。
给本轮真实 diff 和新快照；无法确定归属或证据适用性时标待确认。
```

## 4. 把不熟悉的跨栈代码变成业务可审阅材料

```text
请先不要重构或改代码，帮助我审阅 <任务>。
我熟悉业务，但不完全熟悉当前平台的实现惯例。
先给“输入条件—原行为—期望新行为—代码位置—验证证据”规则表，
重点覆盖默认值、异常状态、功能关闭和状态切换。
再找同仓库一到两个相近实现，说明本次沿用了什么、偏离了什么及必要性。
将业务逻辑问题、平台惯例问题、纯风格建议分开；不要把个人偏好当成缺陷。
最后给最值得我判断的三个问题和原始代码入口。
```
